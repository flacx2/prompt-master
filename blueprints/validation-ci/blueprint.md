## 1. Project Overview & Non-Goals

### Vision

`prompt-master` is a Claude Skill with no code in it: `SKILL.md`, `README.md` and two reference
files, which together route a rough request to one production-ready prompt for a named AI tool. Its
correctness is entirely a property of its prose — a heading that moved, a count that no longer
matches the table it describes, a reference link pointing at a file that was renamed. Nothing in the
repository can currently detect any of that. The only enforcement is a maintainer noticing, and the
git history shows the failure mode landing at least once already: `ab419d6 docs: synchronize pattern
reference count` is a bug fix for a number that drifted.

This change gives the repository its first executable statement of its own rules: a
standard-library Python validator with seven named rules, a negative-fixture self-test that proves
each rule can still fail, and a blocking GitHub Actions check. Nothing in `SKILL.md`, `README.md`,
`LICENSE` or `references/` is touched — this fork tracks `nidhinjs/prompt-master`, so the change is
new files only and upstream merges stay conflict-free.

The modules this change touches: none of them. It reads `SKILL.md`, `README.md`,

`.github/`, `.githooks/`, `.claude/` and the three new root files the bundle's `workspace/` lands.

Five conventions the change must respect, read out of the files themselves:

1. **The three-zone layout of `SKILL.md` is positional.** `## PRIMACY ZONE` (identity, hard rules,
   output lock) at line 7, `## MIDDLE ZONE` (intent extraction, tool routing, diagnostics) at line
   44, `## RECENCY ZONE` (verification, success lock) at line 474. The order is the mechanism.
2. **Tool routing is a flat run of bold blocks**, roughly twenty-five of them (`**Claude Code**`,
   `**Cursor / Windsurf**`, `**ComfyUI**`, and so on), not nested headings.
3. **Reference files are lazy-loaded, never inlined.** Both files under `references/` open by
   telling the reader when to load them.
4. **Counts are synchronised across files by hand.** `references/patterns.md` holds 37 numbered
   rows; `references/templates.md` holds 13 `## Template ` headings; five claim strings elsewhere
   state those two numbers. `ab419d6` exists because one of them drifted.
5. **Length is under pressure.** `9d64012` reads "compress sections under 450 lines"; `SKILL.md` is
   496 today. Additions are expected to pay for themselves.

### Users

| Persona | What they come to do | Frequency |
|---|---|---|

### Goals — v1 scope

1. Seven named rules, each individually runnable, each deriving its expected values from the files
   that own them rather than from a stored number.
2. A self-test that proves every rule still fails on a broken fixture, so no rule can quietly become
   a gate that cannot fail.
3. A blocking GitHub Actions check on `pull_request` and on `push` to `main`, with both actions
   pinned by commit SHA and workflow permissions limited to `contents: read`.
4. Zero bytes changed in `SKILL.md`, `README.md`, `LICENSE` or anything under `references/`, so
   upstream merges remain conflict-free.
5. Zero dependencies: no manifest, no lockfile, no third-party import, nothing to audit or upgrade.

### Non-Goals — explicitly out of scope for v1

| Not building | Why not now | Revisit when |
|---|---|---|
| **Model-pin staleness checking** — flagging `Model Recency Gate` entries that have aged out | It is the churn that actually recurs (five "refresh routing" commits), but there is no `last-verified` marker in `SKILL.md` to read, and adding one edits a file this change may not touch | The fork stops tracking `nidhinjs/prompt-master`, or upstream adds a date marker of its own |

| **Markdown linting in general** — heading hierarchy, table formatting, link style | Upstream's style is upstream's choice; a generic linter would report hundreds of findings on content nobody here may change | Never, while this is a tracked fork |

## 4. Data Model

There is no database. The entities are the artifacts under validation and the records the validator
produces about them — and they are a real contract, because §5's JSON output and §9's gates both
depend on their exact shape.

### Entities

**`SkillFrontmatter`** — the YAML block at the top of `SKILL.md`, delimited by a line of `---`
before and after. Flat; one `key: value` per line; no nesting, no lists.

| Field | Type | Constraints | Notes |
|---|---|---|---|
| `name` | string | required · must equal the repository directory name, `prompt-master` | The skill loader keys on it |
| `version` | string | required · `MAJOR.MINOR.PATCH`, digits only | `1.8.0` today. The `version-sync` rule requires the rendered form to appear in `README.md` |
| `description` | string | required · non-empty | Not length-checked: upstream owns its wording |

**`CountTruth`** — a number the repository defines, derived at run time, never stored.

| Field | Type | Constraints | Notes |
|---|---|---|---|
| `kind` | string | `patterns` or `templates` | The two count families that exist |
| `truth_file` | path | `references/patterns.md` · `references/templates.md` | From `scripts/validator-config.json` |
| `value` | int | counted at run time | `patterns` counts lines matching a numbered-table-row regex; `templates` counts lines beginning `## Template `. On the tree at `2bd9251`: 37 and 13 |

**`CountClaim`** — a number the documents assert about a `CountTruth`.

| Field | Type | Constraints | Notes |
|---|---|---|---|
| `kind` | string | `patterns` or `templates` | |
| `path`, `line` | path, int | 1-based | Where the claim sits |
| `value` | int | must equal the matching `CountTruth.value` | |
| `text` | string | the matched substring | Printed in the finding so the claim is identifiable |

The five claims on the current tree, all agreeing with truth: `SKILL.md:496` "37-pattern",
`README.md:287` "37 Credit-Killing Patterns", `README.md:246` "13 Prompt Templates",
`README.md:251` "13 templates", `references/patterns.md:3` "37 patterns".

**Scan boundary — not an optimisation, a correctness rule.** The `Version History` section of
`README.md` describes past releases; its `1.1.0` entry reads "35 credit killing patterns" and always
will. Claim scanning of `README.md` therefore stops at that heading, which is why the `counts` rule
is green today. The marker is the `claim_scan_stop_markers` entry in the config.

**`Finding`** — the single record type every rule returns and every output format renders.

| Field | Type | Constraints | Notes |
|---|---|---|---|
| `rule` | string | one of the seven registry keys | |
| `path` | string | repository-relative, forward slashes | Never absolute, never backslashed, so output is identical on Windows and on the runner |
| `line` | int or null | 1-based when known | `null` for a whole-file finding |
| `message` | string | one line, no newline | States what was expected and what was found |

**`BudgetEntry`** — one row of the `files` object in `scripts/validator-config.json`.

| Field | Type | Constraints | Notes |
|---|---|---|---|
| `path` | path | key of the `files` object | |
| `max_lines` | int | the ceiling the `budgets` rule enforces | 520 · 450 · 110 · 470 |
| `counted_at_authoring` | int | what the file measured on 2026-10-21 | 496 · 422 · 82 · 442. Informational: it records the headroom each ceiling was chosen with, and no rule compares against it |

### Relationships

- `SkillFrontmatter` —(1:1)→ `SKILL.md`. No cascade; nothing is ever written.
- `CountTruth` —(1:many)→ `CountClaim`. A claim whose kind has no truth file is not a finding; a
  claim whose value differs from its truth is one.
- Rule —(1:many)→ `Finding`. Zero findings from every rule that ran is exit 0.
- `BudgetEntry` —(1:1)→ a file on disk. A `files` key with no file on disk is a config error, exit 2,
  not a finding about the tree.

### Indexes

NOT APPLICABLE — no database. The documents are read once per run into a map keyed by
repository-relative path, which is the only lookup structure the program has.

### Schema

The machine-readable contract is the JSON output, defined once here and asserted by §9 step 10:

```json
{
  "tool": "validate_skill",
  "repo_root": "/abs/path/to/prompt-master",
  "rules_run": ["frontmatter", "counts", "zones", "links", "budgets", "version-sync", "encoding"],
  "findings": [
    {
      "rule": "counts",
      "path": "README.md",
      "line": 287,
      "message": "claims 36 patterns; references/patterns.md defines 37"
    }
  ],
  "exit_code": 1
}
```

`findings` is `[]` and `exit_code` is `0` on a clean run. `rules_run` lists the rules that actually
ran, so a single-rule run is distinguishable from a full one.

### Migrations

NOT APPLICABLE — there is no persistent store to migrate. `scripts/validator-config.json` is read at
every run and its shape changes only by editing the file.

### Seed data

NOT APPLICABLE as a database concept. The equivalent is the fixture set under
`scripts/tests/fixtures/`, authored by step 9: one deliberately broken tree per rule, which
`--self-test` reads. No rule reads them on a normal run, because no rule reads anything the config
does not name.

## 5. API Design

The interface is a command-line program. It is the whole public surface, and §9's gates, the
workflow and the hook all consume it, so it is specified here in full.

### Conventions

- Invocation: `python scripts/validate_skill.py` with the options below, run from the repository
  root.
- Repository root: the parent of `scripts/`, derived from the script's own location — never the
  current working directory, so the hook and the workflow get the same answer.
- Config path: `scripts/validator-config.json`, overridable with `--config`.
- Response envelope — one shape per format, no exceptions:
  - default (`text`): one line per finding, `<path>:<line>: <rule>: <message>`, with the line number
    omitted as `<path>: <rule>: <message>` when it is null, then one trailing summary line.
  - `--format json`: exactly the object in §4's *Schema*, on stdout, and nothing else on stdout.
  - `--format github`: one `::error file=<path>,line=<line>::<rule>: <message>` per finding, which is
    the annotation syntax GitHub Actions renders inline on the diff.
- Error codes — the enumerated set, and they are a contract:

| Exit | Meaning | Example |
|---|---|---|
| `0` | Every rule that ran produced no finding | a clean tree |
| `1` | At least one finding | a drifted count |
| `2` | The validator's own usage error | unknown flag, unknown rule name, missing or unparseable config, a file named in `files` that cannot be read |

- Never collapse `2` into `1`. A gate whose pass condition were merely "non-zero" would accept a
  typo in its own flag as proof the repository is broken. §9 step 1 gates on the distinction.
- Validation: `argparse` rejects unknown flags with its own exit 2, which this program adopts
  deliberately rather than overriding. An unknown rule name is checked against the registry and also
  exits 2.
- Pagination, idempotency, rate limits: NOT APPLICABLE — a synchronous local run with no state.

### Routes

The flag surface stands in for routes. Every one of these is exercised by a §9 gate.

| Flag | Argument | Description | Introduced by | Exit behaviour |
|---|---|---|---|---|
| none | — | Run every registered rule | step 1 | 0 / 1 |
| `--version` | — | Print the tool name and version, then exit | step 1 | 0 |
| `--list-rules` | — | Print one registered rule name per line, in run order | step 1 | 0 |
| `--rule` | rule name | Run exactly one rule | step 1 | 0 / 1 / 2 on an unknown name |
| `--config` | path | Use a different config file | step 1 | 0 / 1 / 2 if missing or unparseable |
| `--root` | path | Validate a different tree — the mechanism `--self-test` uses on fixtures | step 9 | 0 / 1 / 2 |
| `--self-test` | — | Run every rule against every fixture and assert each fixture fails its own rule and no other | step 9 | 0 / 1 |
| `--format` | `text` · `json` · `github` | Output format, default `text` | step 10 | as above |

### Critical endpoints — full detail

**`python scripts/validate_skill.py`** — the default run.

- Reads `scripts/validator-config.json`. Missing, unreadable or not valid JSON exits 2 with
  `config: <reason>` on stderr.
- Builds the file map: every path in `files`, plus `skill_file` and `readme_file`, read as bytes,
  decoded UTF-8, CRLF normalised to LF. An undecodable file is a finding from `encoding`, not a
  crash. A path in `files` that does not exist on disk exits 2, because the config is wrong rather
  than the tree.
- Runs the seven rules in registry order, collecting findings.
- Prints the findings, then the summary line. Exit 1 if there is any finding, else 0.
- Writes nothing, anywhere, ever.

**`python scripts/validate_skill.py --self-test`** — the proof that the gates can fail.

- For each directory under `scripts/tests/fixtures/`, runs every rule against that directory as the
  root.
- Asserts that the rule of the same name produces at least one finding, and that every other rule
  produces none.
- Prints one line per fixture and a summary.
- Exits 0 when every fixture behaves, 1 otherwise, naming the fixture and the unexpected rule.

**The seven rules**, each with what it asserts and where it comes from:

| Rule | Asserts | Reads | Introduced by |
|---|---|---|---|
| `frontmatter` | `SKILL.md` opens with a delimited block carrying `name`, `version` and `description`; `name` equals the repository directory name; `version` matches `MAJOR.MINOR.PATCH` | `SKILL.md` | step 3 |
| `counts` | Every pattern-count and template-count claim equals the number derived from the file that owns it, with `README.md` scanned only above its `Version History` heading | all four documents | step 4 |
| `zones` | `## PRIMACY ZONE`, `## MIDDLE ZONE` and `## RECENCY ZONE` each appear exactly once in `SKILL.md`, in that order | `SKILL.md` | step 5 |
| `links` | Every `references/` path mentioned in `SKILL.md` or `README.md` exists on disk; every in-file anchor link in `references/templates.md` resolves to one of its own headings under GitHub's slug rules | `SKILL.md`, `README.md`, `references/templates.md` | step 6 |
| `budgets` | Every file in the config's `files` map is at or under its `max_lines` | the `files` map | step 2 |
| `version-sync` | The frontmatter version, rendered in bold, appears somewhere in `README.md` | `SKILL.md`, `README.md` | step 7 |
| `encoding` | Every document decodes as UTF-8, carries no byte-order mark, and ends with exactly one newline | the `files` map | step 8 |

### Interfaces held constant

The change may not move any of these. Each is mirrored as a row in §1's Non-Goals table.

## 9. BUILD ORDER

Twelve steps, each sized for one sitting, each touching at most five files and carrying at most six
acceptance criteria. Every `Verify` line exits 0 when the step is correct — where the correct outcome
of a command is a failure, the expected exit code is asserted explicitly, so a usage error cannot
satisfy the gate. No `Verify` block asserts anything its own `Checkpoint` produces: at the moment a
gate runs, that step's files are written but untracked and its tag does not exist.

Two standing constraints, repeated here because they bind every step:

- **`SKILL.md`, `README.md`, `LICENSE` and everything under `references/` are read-only.** No step
  edits them. A rule that would need one of them edited to pass is a wrong rule.
- **Standard library only.** No step installs anything, because there is nothing to install.

#### Step 1 — Validator harness, exit-code contract, and the `budgets` rule

**Do**

Create `scripts/validate_skill.py`, standard library only, with:

- `Finding` as a small immutable record carrying `rule`, `path`, `line`, `message` — the shape §4
  fixes. `path` is always repository-relative with forward slashes, produced by one helper so no rule
  can emit a Windows path.
- `load_config(path)` — reads JSON, exits 2 with `config: <reason>` on stderr if it is missing,
  unreadable or invalid.
- `build_context(root, config)` — reads every path in the config's `files` object plus `skill_file`
  and `readme_file` as bytes, decodes UTF-8, replaces CRLF with LF, and exposes the result as a map
  keyed by repository-relative path. A listed file that is absent exits 2 (the config is wrong, not
  the tree). A file that cannot be decoded is recorded with its raw bytes and no text, so the
  `encoding` rule added in step 7 can report it instead of the program crashing.
- **No rule walks the tree, and none may be written to.** The file set is exactly what the config
  names, which is why the validator cannot be surprised by a file somebody adds later.
  `exclude_dirs` is therefore enforced as a *guard* rather than as a filter:
  `assert_not_excluded(path, config)` exits 2 when **the `--config` path**, a configured document
  path, a `--root`, or a fixture directory resolves inside any entry in `exclude_dirs` — the
  `--config` path included, because the bundle's `workspace/` carries its own copy of the config and
  that copy is the most likely thing anyone points at by accident. `exclude_dirs` already lists
  `blueprints`, `.git`,
  `.github`, `.claude`, `.claude-flow`, `.swarm`, `scripts/tests/fixtures` and `__pycache__`. The
  bundle sits inside the repository it validates and its `workspace/` holds a differently-tuned copy
  of the config, so pointing the validator into the bundle is a mistake worth refusing out loud
  rather than a tree to filter quietly — see §19.6. `--self-test` applies the same list when it
  enumerates fixture directories, so a stray `__pycache__` there is never mistaken for a fixture.
- `RULES`, an ordered mapping from rule name to function. Step 1 registers exactly one: `budgets`.
- `rule_budgets(ctx)` — one finding per file whose line count exceeds its `max_lines`, worded
  `<n> lines exceeds the ceiling of <max_lines>`. **Line count is the number of newline-terminated
  lines — `len(text.splitlines())`, which is what `wc -l` reports** and what the 496 / 422 / 82 / 442
  figures in §1 and §4 were measured with. Splitting the text on the newline character instead yields
  one more than that on a file that ends in a newline, which every document here does, so a finding
  would name a number nobody can reproduce with `wc`.
- **Config-shape validation belongs to `load_config`, never to a rule.** A `files` entry whose
  `max_lines` is absent or not an integer, or whose key is not a string, exits 2 — and it does so
  from the loader, because a rule is a pure function that returns findings and never calls
  `sys.exit` (`.claude/rules/validator.md`). Validate the whole `files` map once, at load, and every
  rule can then trust its shape.
- `argparse` wiring for `--version`, `--list-rules`, `--rule`, `--config`, and the no-flag default
  run. An unknown `--rule` name exits 2 after printing the registry. `--version` prints exactly
  `validate_skill 1.0.0` — the tool's own version, which starts at `1.0.0` here and is bumped by hand
  when the output contract in §5 changes, so a consumer parsing the JSON has something to pin
  against. `--config` is resolved relative to the current working directory, and every command in
  this blueprint runs from the repository root.
- A reporter that prints `<path>:<line>: <rule>: <message>`, or `<path>: <rule>: <message>` when the
  line is null, followed by one summary line. Exit 1 if there is any finding, else 0.
- A guard that exits 2 with a named error if the interpreter is older than 3.9.

The file never writes anything and never imports outside the standard library.

**Done when**

- [ ] WHEN `python scripts/validate_skill.py --version` runs THE SYSTEM SHALL print a version line and exit 0.
- [ ] WHEN `python scripts/validate_skill.py --list-rules` runs THE SYSTEM SHALL print `budgets` and exit 0.
- [ ] WHEN `python scripts/validate_skill.py` runs against this repository THE SYSTEM SHALL report zero findings and exit 0, because every document is under its ceiling.
- [ ] WHEN an unknown flag is passed THE SYSTEM SHALL exit 2 and SHALL NOT exit 1, so a malformed command can never be mistaken for a failing repository.
- [ ] WHEN `--rule no-such-rule` is passed THE SYSTEM SHALL exit 2 and print the registered rule names.
- [ ] WHEN `--config` names a file that does not exist THE SYSTEM SHALL exit 2 with a message beginning `config:`.

**Verify**

```bash

python scripts/validate_skill.py --version | grep -qx 'validate_skill 1.0.0'   # expect: exit 0 — the literal §5 fixes
python scripts/validate_skill.py --list-rules | grep -qx budgets   # expect: exit 0 — the rule is registered
python scripts/validate_skill.py                                   # expect: exit 0, zero findings
python scripts/validate_skill.py --rule budgets                     # expect: exit 0
```

#### Step 2 — `frontmatter` rule

**Do**

Add `rule_frontmatter(ctx)` to `scripts/validate_skill.py` and register it after `budgets`. It reads
the config's `skill_file` and asserts:

- The text opens with a delimiter line, then `key: value` lines, then a closing delimiter line. A

#### Step 3 — `counts` rule

**Do**

Add `rule_counts(ctx)` and register it. For each entry under the config's `counts` object:

- Derive the truth from `truth_file`. `truth_kind` `numbered_table_row` counts lines matching a
  numbered Markdown table row — a leading pipe, optional spaces, one or more digits, optional
  spaces, a pipe. `truth_kind` `template_heading` counts lines beginning with the literal
  `## Template `. On this repository the two truths are 37 and 13; the rule derives them at run time
  and stores neither.
- Scan every document in the file map for claims of that kind, matching a number followed by at most
  one intervening word and then the noun — this is what matches `37 patterns`, `37-pattern`,
  `37 Credit-Killing Patterns`, `13 templates` and `13 Prompt Templates` alike, case-insensitively.
- **Stop scanning a file at its marker in `claim_scan_stop_markers`.** For `README.md` the marker is
  the Version History heading, below which the `1.1.0` entry states a historical count of 35 that
  must never be reported. A file with no marker is scanned whole.
- Emit one finding per claim whose value differs from its truth, worded
  `claims <claimed> <kind>; <truth_file> defines <truth>`, carrying the 1-based line of the claim.
- A `counts` entry whose `truth_file` is absent from the tree, or whose `truth_kind` is unknown,
  exits 2 — that is a broken config, not drift.

**Done when**

- [ ] WHEN the rule runs against this repository THE SYSTEM SHALL report zero findings, because every pattern claim equals the number of numbered rows in the patterns reference and every template claim equals the number of template headings in the templates reference.
- [ ] WHEN a claim states a number that differs from its derived truth THE SYSTEM SHALL report one finding at that claim's line, naming both numbers.
- [ ] WHEN a historical claim appears below the configured stop marker THE SYSTEM SHALL report nothing for it.
- [ ] WHEN a configured truth file is missing from the tree THE SYSTEM SHALL exit 2 rather than report a finding.
- [ ] WHEN the number of rows in the patterns reference changes and the claims are updated to match THE SYSTEM SHALL stay silent without any edit to this rule.

**Verify**

```bash
python scripts/validate_skill.py --list-rules | grep -qx counts   # expect: exit 0
python scripts/validate_skill.py                                   # expect: exit 0 — three rules clean
```

#### Step 5 — `links` rule

**Do**

Add `rule_links(ctx)` and register it. Two checks, both over text the file map already holds:

- **Reference paths.** Every mention of a path under `references/` ending in `.md`, in the skill file
  or the readme, must exist on disk. One finding per missing path, at its line.
- **In-file anchors.** In the templates reference, every Markdown link whose target begins with `#`
  must resolve to a heading in that same file. The slug is computed the way GitHub computes it:
  lowercase the heading text, drop every character that is not a word character, whitespace or
  hyphen, then replace each whitespace run with a single hyphen. On this repository that makes the
  table-of-contents link for `Template A — RTF` resolve to the heading of the same name, and all
  thirteen resolve today.

Emit one finding per unresolved anchor, carrying the line of the link and the slug that was not
found.

**Done when**

- [ ] WHEN the rule runs against this repository THE SYSTEM SHALL report zero findings, because both reference paths exist and every in-file anchor in the templates reference resolves to a heading in that file.
- [ ] WHEN a mentioned reference path does not exist THE SYSTEM SHALL report one finding at the mention's line.
- [ ] WHEN an in-file anchor names a slug no heading produces THE SYSTEM SHALL report one finding carrying that slug.
- [ ] WHEN a heading contains an em dash THE SYSTEM SHALL compute the same slug GitHub does, so a correct table-of-contents entry is not reported.

**Verify**

#### Step 7 — `encoding` rule

**Do**

Add `rule_encoding(ctx)` and register it last. For every file in the map it asserts, according to the
config's `encoding` object:

flip it without reading §1's Non-Goals.

#### Step 10 — `--format json` and `--format github`

**Do**

Add `--format`, defaulting to `text`, with two further values. Formatting happens in the reporter
only, so the three outputs cannot drift from each other.

- `json` prints exactly the object §4's *Schema* fixes: `tool`, `repo_root`, `rules_run`, `findings`

## 13. Testing Strategy

Tests exist here to make §9's acceptance criteria checkable, and the shape they take is unusual
because the thing under test is a validator: the interesting property is not "does it pass on good
input" but "does it still fail on bad input".

| Layer | Framework | What it covers | Where | Runs |
|---|---|---|---|---|
| Rule-level positive | the validator itself | each rule against the real repository, which must be clean | `--rule <name>` | every step from 1 to 12, and in CI |
| Rule-level negative | the validator itself, over fixtures | each rule against a tree built to break it, which must fail | `scripts/tests/fixtures/<rule>/` via `--root` | steps 8 and 9, and in CI through `--self-test` |
| Isolation | the validator itself | each fixture breaks exactly one rule and no other | `--self-test` | step 9 onwards, and in CI |
| Syntax | `python -m compileall` | the validator parses on the pinned interpreter | `scripts/` | every step, and in CI |
| Config integrity | `python -m json.tool` | the config is valid JSON | `scripts/validator-config.json` | step 12, and in CI |

### Critical flows to cover

1. **A drifted count is caught.** The `counts` fixture states a number that disagrees with its own
   patterns reference; the rule must report it, and must report nothing for the historical claim
   below the stop marker.
2. **A moved zone is caught.** The `zones` fixture transposes two zone headings; the rule must report
   the order violation.
3. **A broken anchor is caught.** The `links` fixture carries a table-of-contents link whose slug no
   heading produces.
4. **A usage error is not mistaken for a finding.** An unknown flag, an unknown rule name and a
   missing config each exit 2, and §9 step 1 asserts the code rather than merely "non-zero".

### Test data

The fixture trees are the test data, authored by steps 8 and 9, committed, and excluded from every
normal run by `exclude_dirs`. Each is a minimal four-document tree plus, where the rule needs
different tuning, its own `validator-config.json` — which is how the `budgets` fixture demonstrates a
ceiling breach with a one-line ceiling instead of a 521-line document. No test shares mutable state
with another, because no test writes anything at all.

### What is deliberately not tested

- **The content of the skill's advice.** Whether a generated prompt is good is not mechanically
  decidable and is not what this change is for.
- **Upstream's prose style.** Heading hierarchy, table formatting and trailing whitespace are
  upstream's choices; see §1's Non-Goals.
- **GitHub's own behaviour.** That a pull request is actually blocked depends on branch protection,
  which is a repository setting no script here can read or set. It is in §20.1's launch checklist.

## 20. Acceptance Gate, Risks & Decision Log

### 20.1 Global acceptance gate

The change is **done** when every command below exits 0 on a clean checkout, run from the repository
root, and not before. This is the same set CI runs and the same set every §9 step is measured
against.

```bash
python --version                                                    # expect: exit 0, 3.9 or newer
python -m compileall -q scripts                                     # expect: exit 0
python -m json.tool scripts/validator-config.json > /dev/null        # expect: exit 0 — the config parses
python scripts/validate_skill.py --list-rules                        # expect: exit 0, one rule per line
python scripts/validate_skill.py --self-test                         # expect: exit 0 — every fixture fails its own rule and no other
python scripts/validate_skill.py                                     # expect: exit 0, zero findings
python scripts/validate_skill.py --format json | python -m json.tool > /dev/null   # expect: exit 0
python scripts/validate_skill.py --format github                     # expect: exit 0, no annotations on a clean tree
sh .githooks/pre-commit                                              # expect: exit 0 — the local gate agrees with CI
python scripts/validate_skill.py --not-a-flag; test $? -eq 2         # expect: exit code 2 -> this line exits 0
git diff --quiet HEAD -- SKILL.md README.md LICENSE references        # expect: exit 0 — upstream content byte-identical
```

Every expectation above is a property rather than a tally, with one deliberate exception: the rule
count, which is asserted as `7` in §9 step 7 because seven is what §5's rule table defines and what
the fixture set must cover. It appears identically in §1's goals, §5's rule table, §9 step 7, §19.6's
cross-artifact row and both epic files.

Every line exits 0 on a correct build. The one line whose correct outcome is a failure — the unknown
flag — asserts the specific code `2` rather than merely "non-zero", so a malformed command cannot
satisfy it.

| 1 | Python 3, standard library only | Node with a small package set; Bash with `grep` and `awk` | Python is already on the machine and on every runner, and it keeps the repository manifest-free. | 8 | `encoding` tolerates CRLF | Forbidding CRLF, the usual default | Every committed blob is CRLF and `core.autocrlf` is `true` locally. Forbidding it is red on day one and fixable only by rewriting all four documents, which guarantees the next upstream merge conflicts | Decision 2 reverses |
| 9 | Fixtures are minimal four-document trees, each with its own optional config | One shared fixture tree with per-rule mutations applied at run time | A tree on disk is readable in a diff and needs no fixture framework. The optional per-fixture config is what lets `budgets` demonstrate a breach with a one-line ceiling instead of a committed 521-line file | The fixture set grows past the point where the duplication is worse than a generator — which, with seven small trees, it is not |
| 10 | The hook is a convenience; CI is the gate | Relying on the hook alone; or a `pre-push` hook | A hook is bypassable with `--no-verify` and absent on a fresh clone until `core.hooksPath` is set once. CI is the only enforcement a maintainer cannot forget | Never: this is the standard reason hooks are not gates |
| 11 | One file, `scripts/validate_skill.py`, rather than a package | `scripts/validator/` with a module per rule | Seven rules of a few lines each. A package would add `__init__.py`, an import convention and a resolution question (§19.6) that currently does not exist anywhere in this stack | The registry passes roughly fifteen rules, or a rule needs its own test file |
| 12 | `compileall` plus `json.tool` as the lint/format gate | `ruff`, `black`, `flake8` | They are third-party, and there is one Python file for a formatter to have an opinion about. The gate answers the only question that matters — does it parse — with zero dependencies | A second or third Python file appears, or more than one person edits the validator |

### 20.4 What to build next

In order, each with its trigger from §1's Non-Goals table:

1. **Model-pin staleness checking** — the churn that actually recurs. Needs a `last-verified` marker
   in `SKILL.md`, so it waits on the fork stopping its upstream tracking, or on upstream adding a
   date marker of its own. This is the first thing to build the moment decision 2 reverses.
2. **CRLF normalisation and trailing-whitespace enforcement** — two rules and one normalising commit,
   available together the moment the fork diverges deliberately.
3. **A counts manifest the documents read from**, replacing the derive-and-compare `counts` rule with
   a single source the prose cites. Same trigger.
4. **A `--fix` flag** for the drift the rules can repair mechanically — a count claim, a version
   string. Only meaningful once writing to the four documents is allowed.
5. **Dropping the rules native tooling already covers**, if `claude plugin eval` or `/skill-doctor`
   turns out to own `frontmatter` and `links`. Trigger: the ten-minute check at the start of the
   build says so.
